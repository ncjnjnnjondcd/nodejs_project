# Вибір технологій для todo_nodejs

* **Автори:** Мартинюк Максим ІО44

## 1. Контекст і постановка проблеми
Необхідно розробити легкий і продуктивний вебзастосунок для відстежування задач зі статусами (TODO, IN_PROGRESS, DONE), пріоритетами, термінами виконання та фільтрацією

Головні технічні вимоги:
* Використання **Node.js** 
* Відмова від важких фронтенд-фреймворків (React, Angular, Vue) для максимального спрощення кодової бази
* Забезпечення високої швидкості розробки, строгої типізації та простоти локального запуску


## 2. Критерії прийняття рішення
* Модульність архітектури бекенду та вбудована валідація даних задач (DTO)
* Простота роботи з даними (моделі задач, статусів і пріоритетів)
* Єдине середовище виконання (один процес Node.js роздає і API, і статичний інтерфейс)


## 3. Розглянуті варіанти

### Варіант 1: NestJS (REST API) + Vanilla JS / HTML5 / CSS3 (роздача через @nestjs/serve-static)
* **Плюси:** 
  * Повна відсутність сторонніх фронтенд-бандлерів і залежностей
  * Фронтенд складається з чистих статичних файлів (`public/index.html`, `public/app.js`), які віддаються тим самим NestJS-сервером
  * Інтерактивність досягається через нативні `fetch()`-запити та DOM API
* **Мінуси:** Відсутність реактивного зв'язування даних «з коробки» (DOM оновлюється вручну через нативний JS)

### Варіант 2: NestJS + SSR (Server-Side Rendering через Handlebars/EJS)
* **Плюси:** Рендеринг сторінок цілком на сервері без клієнтського JS
* **Мінуси:** Будь-яка зміна статусу або видалення задачі вимагає перезавантаження сторінки або надсилання форм, що знижує плавність інтерфейсу порівняно з REST + `fetch`

---

## 4. Прийняте рішення
Обрано **Варіант 1: NestJS (CJS + TypeScript) + Vanilla JS / HTML5 + SQLite через Prisma ORM**

Пояснення:
1. **NestJS для бекенду:** Надає чітку модульну структуру і сувору валідацію вхідних полів задач через `class-validator`
2. **Vanilla JS для фронтенду:** Ідеально відповідає вимозі не використовувати фреймворки, гарантує миттєве завантаження сторінки в браузері та відсутність зайвих `node_modules` для UI
3. **`@nestjs/serve-static`:** Дозволяє об'єднати бекенд і UI в єдиний сервіс без необхідності налаштування Nginx на етапі розробки.
4. **SQLite:** Збереження оперативної пам'яті та памяті на диску, швидкість старту
5. **Prisma ORM:** Забезпечує строгу типізацію (Type-Safety) сутності `Task`, автоматичні міграції схемы та зручний доступ до SQLite без необхідності писати сирі SQL-запити вручну

## 5. Наслідки рішення

### Позитивні
* Єдиний `package.json` і єдиний репозиторій для всього додатку
* Немає конфліктів версій між фронтенд-бібліотеками
* Зрозумілий і прозорий код для вивчення нативних можливостей браузера та NestJS

### Негативні / Компроміси
* При ускладненні інтерфейсу логіку маніпуляцій з DOM доведеться писати вручну на чистому JS
* SQLite блокує файл бази на час запису
