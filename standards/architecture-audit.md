## Топ-3 перевірені залежностей

| Пакет | Використання | Висновок |
| :--- | :--- | :--- |
| @prisma/client | src/prisma.service.ts | Потрібен для доступу до БД SQLite, runtime dependency |
| class-validator | src/tasks/dto/ | Потрібен для валідації вхідних DTO у запитах, runtime dependency |
| oxlint | package.json, pre-commit hook | Потрібен для швидкої статичної перевірки коду, devDependency |

#### Межі простого рішення
* **Збірка:** `nest build` компілює TypeScript у `dist/`; клієнтська статика (`public/`) роздається через `@nestjs/serve-static`.
* **Хуки та fail-fast:** У `.husky/pre-commit` для перевірок `lint-staged` та `npm run typecheck`, що гарантує негайне блокування коміту при першій же помилці лінтера чи типів.
* **Обмеження:** Застосунок використовує локальну файлову БД SQLite.
* **Відтворюваність:** Версії залежностей зафіксовані в `package.json` та `package-lock.json`; детерміноване встановлення в чистому середовищі перевіряється командою `npm ci`.

На поточній ітерації реалізовано **бар'єр валідації вхідних даних та маршрутизації**:
1. **Ізоляція та валідація на рівні контролера:** 
   * Усі вхідні HTTP-запити (`POST`, `PATCH`) проходять крізь конвеєр `ValidationPipe` та перевіряються правилами `class-validator` (`CreateTaskDto`, `UpdateTaskDto`).
   * Порожній заголовок `title`, невідомий `status` чи неправильний `priority` блокуються ще до передачі в сервісний шар зі статусом `400 Bad Request`.
2. **Стан сервісного шару та БД (Stub Mode):**
   * Модель сутності та переліки (`enum`) типізовані в `prisma/schema.prisma`.
   * Бізнес-логіка в `TasksService` на поточному етапі працює в режимі  заглушки і підтверджує узгодженість DTO, не виконуючи фінальних мутацій у файлі `dev.db`.
3. **Клієнтський UI (`public/`):**
   * Директорію створено під роздачу статичного інтерфейсу (`@nestjs/serve-static`), рендеринг DOM є наступним завданням.
