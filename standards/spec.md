# Архітектурна специфікація: Task Tracker System (spec.md)

## 1. Загальний опис системи
Система є легким вебзастосунком для управління особистими та робочими завданнями:
* **Клієнтський шар (Vanilla Web Client):** чистий HTML5, CSS3 та JavaScript (Fetch API + DOM API) без використання важких фронтенд-фреймворків (React, Vue, Angular) та окремих бандлерів (Webpack/Vite)
* **Серверний шар (NestJS REST API):** модульний бекенд на Node.js із суворою типізацією TypeScript, валідацією DTO через `class-validator` та вбудованим сервером роздачі статичних файлів (`@nestjs/serve-static`)
* **Шар збереження даних:** реляційна вбудована база даних **SQLite** (`prisma/dev.db`), взаємодія з якою реалізована через **Prisma ORM** (End-to-End Type Safety)


## 2. Розбиття на компоненти/модулі та взаємодія

### 2.1. Опис компонентів та модулів
1. **Frontend (`public/`):**
   * `index.html` (View): розмітка форми додавання задач, панелі фільтрів (статус, пріоритет) та контейнера списку завдань
   * `style.css` (Styles): оформлення інтерфейсу, кольорові індикатори пріоритетів (LOW, MEDIUM, HIGH) та адаптивна верстка
   * `app.js` (Client Controller): асинхронні виклики через нативний `fetch()` до REST API, перехоплення подій форм та динамічне оновлення DOM без перезавантаження сторінки

2. **Backend (`src/`):**
   * `AppModule`: кореневий модуль; реєструє `ServeStaticModule` (роздача директорії `public/`), `PrismaModule` та `TasksModule`
   * `ServeStaticModule`: транслює статичні файли клієнта на порт сервера, виключаючи префікс `/api/(.*)`
   * `TasksModule`:
     * `TasksController`: описує маршрути `/api/tasks`, мапить Query/Body параметри та валідує вхідні DTO
     * `TasksService`: реалізує бізнес-логіку (фільтрація, зміна статусів, сортування за датою створення)
     * `CreateTaskDto` / `UpdateTaskDto`: валідація полів через `class-validator` (заборона порожніх назв, контроль допустимих значень enum)
   * `PrismaModule` & `PrismaService`: шар абстракції бази даних; керує життєвим циклом підключення до файлу `dev.db` (SQLite) через Dependency Injection (DI)

### 2.2. Взаємодії компонентів
 
### 2.2. Опис взаємодії компонентів

1. **Клієнтська частина (Vanilla UI):** Користувач взаємодіє з інтерфейсом у браузері (створення, фільтрація, перемикання статусу чи видалення завдання) Скрипт `app.js` перехоплює подію через DOM API, запобігає перезавантаженню сторінки (`e.preventDefault()`) і виконує асинхронний HTTP-запит (`fetch()`) із JSON-тілом до REST API сервера
2. **Роздача статики (`ServeStaticModule`):** При зверненні до кореневої адреси застосунку сервер NestJS автоматично віддає файли `index.html`, `style.css` та `app.js` із каталогу `public/`, не блокуючи маршрути з префіксом `/api/`
3. **Контролер (`TasksController`):** Приймає вхідний REST-запит (`/api/tasks`), запускає конвеєр валідації DTO через `class-validator`і передає перевірені параметри у сервісний шар
4. **Бізнес-логіка (`TasksService`):** Обробляє правила предметної області (перевіряє існування запису, задає початковий статус `TODO`, застосовує фільтри) і делегує збереження даних шару ORM.
5. **Шар даних (`PrismaService` → SQLite):** Prisma транслює виклики типізованих методів клієнта у структуровані SQL-команди до локального файлу бази даних `dev.db`
6. **Відповідь та оновлення UI:** Результат операції повертається клієнту у форматі JSON (`200 OK` або `201 Created`), після чого `app.js` точково модифікує відповідні вузли дерева DOM без перезавантаження вебсторінки

### Допустимі значення атрибутів (Enums):
* **TaskStatus:**
  * `TODO` завдання очікує виконання (значення за замовчуванням)
  * `IN_PROGRESS` завдання взято в роботу
  * `DONE` завдання виконано
* **TaskPriority:**
  * `LOW` низький пріоритет
  * `MEDIUM` середній пріоритет (значення за замовчуванням)
  * `HIGH` високий пріоритет


## 4. Оновлення даних за ключовими сценаріями

### Сценарій 1: Створення нового завдання
1. **Користувач:** заповнює поля форми (назва, опис, пріоритет) і натискає «Додати»
2. **Клієнт (`app.js`):** перехоплює подію `submit`, викликає `POST /api/tasks` із тілом JSON
3. **TasksController & ValidationPipe:** контролер валідує `CreateTaskDto`. Якщо поле `title` порожнє або пріоритет не відповідає дозволеним значенням, повертається `400 Bad Request`
4. **TasksService & PrismaService:** сервіс встановлює початковий статус `TODO` та викликає `prisma.task.create()`, зберігаючи запис у файл `dev.db`
5. **Клієнт (`app.js`):** отримує статус `201 Created` і динамічно додає нову картку в DOM-список

### Сценарій 2: Зміна статусу завдання (TODO -> IN_PROGRESS -> DONE)
1. **Користувач:** змінює стан чекбокса або обирає новий статус у картці завдання
2. **Клієнт (`app.js`):** зчитує `id` елемента і відправляє `PATCH /api/tasks/:id` із `{ status: newStatus }`
3. **TasksService:** знаходить запис у базі; якщо його немає — повертає `404 Not Found`. За допомогою `prisma.task.update(...)` записує новий статус і системний час в `updatedAt`
4. **Клієнт (`app.js`):** отримує `200 OK` та візуально оновлює статус картки без перезавантаження сторінки

### Сценарій 3: Фільтрація задач
1. **Користувач:** вибирає фільтр за статусом (наприклад, `TODO`) або пріоритетом (`HIGH`)
2. **Клієнт (`app.js`):** робить запит `GET /api/tasks?status=TODO`
3. **TasksService:** викликає `prisma.task.findMany({ where: { status } })`
4. **Клієнт (`app.js`):** очищує контейнер і рендерить оновлений список відфільтрованих задач

### Сценарій 4: Видалення завдання
1. **Користувач:** натискає кнопку видалення картки
2. **Клієнт (`app.js`):** викликає `DELETE /api/tasks/:id`.
3. **TasksService:** видаляє рядок із SQLite через `prisma.task.delete(...)`
4. **Клієнт (`app.js`):** після статусу `200 OK` видаляє HTML-елемент із дерева DOM
